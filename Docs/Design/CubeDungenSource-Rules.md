# CubeDungenSource 规则梳理

分析日期：2026-09-28。

本文记录原作规则，作为 Dungeon 纯 C# 规则内核的参考基线。新项目的实现与接入见 `Core-Implementation.md`。

**新项目决定：不实现闪避和暴击。** 下文保留原作的相关分析，不能把它们当作 Dungeon 的实现需求。Core 的属性、效果和战斗事件均不含这两种机制。

## 1. 来源与可信度

用户指定目录 `C:\Entertainment\Game\CubeDungenSource` 是 Unity 发布包，包含托管程序集和可读取的资源包，并非 Unity 源工程。本次静态分析了 `Assembly-CSharp.dll` 的反编译结果，并读取 SO 序列化配置交叉核对。

资源版本：Core `2026-09-01-1294`、MainPackage `2026-09-01-1293`、LanguagePackage `2026-09-01-1224`。这是本地包版本，不代表线上最新版本。程序集 SHA-256 和每条配置的资源包、对象 ID 记录在 `CubeDungenSource-Evidence.json`。

本文采用三种结论：

- **代码确认**：在实际执行方法中找到的行为，仍可能存在未覆盖的调用上下文。
- **配置确认**：直接读到 SO 字段或事件配置；不等于该内容一定在正常游戏流程开放。
- **重建建议 / 待确认**：新项目的设计建议，或需要运行验证的行为，不混入原作规则。

已建立配置索引：7 个英雄、60 个非英雄单位、515 条技能结构、55 条状态/说明词条、25 个道具、25 个符文、21 张地图。技能结构包含武器、遗物、怪物技能等；非英雄单位包含召唤物；状态文件也包含纯说明词条。不能将这些数量直接当作玩家可获得内容数量。

配套文件：`CubeDungenSource-ConfigIndex.md` 提供名称、ID、基础数值、参数增量、描述与事件函数索引。原始描述可能过期，冲突时优先看执行代码。

## 2. 核心玩法循环

整体结构是“职业选择与局外成长 → 地块探索 → 战斗/事件/资源选择 → 构筑强化 → 区域推进 → 胜负结算”。

1. 选择英雄与难度，创建本局角色、技能池、背包和遗物集合，应用已获得的成长效果。
2. 从地图入口探索，逐步开放相邻地块。
3. 地块提供战斗、宝箱、金币、钥匙、商店、恢复、事件、升级、符文、区域出口等交互。
4. 遇敌后进入独立的双方回合战斗；玩家管理行动力、生命/魔力、技能冷却和状态组合。
5. 胜利获得奖励并完成地块交互；逃跑返回探索，不能按战斗胜利处理。
6. 按区域条件进入下一张地图；指定终局敌人战败可触发通关。玩家死亡触发失败与局外经验结算。

依据：`PlayerDataManager.InitPlayerData`、`MonsterCubeInteractive.OnClickThis`、`BattleOpreate`、`GlobalEvent.GameOver`。

## 3. 地图与探索

### 3.1 地图拓扑与地块状态

**代码确认：原作使用整数二维坐标和上、右、下、左四方向邻接。** 它不是六边形邻接，也不能因为 `CubeMapData.MaxSize` 存在 `(5,5)` 就认为所有地图固定为 5×5。

每个地块至少保存：坐标、内容 ID、深度参数、是否可点击、是否点击过、是否打开、是否可查看内容、是否揭露邻居、交互是否完成。这些状态不同，例如“看见内容”不等于“完成交互”。

地图内容有空地、战斗、奖励、事件、不可通行、障碍、其他、Boss、出口。地图生成可使用随机池，也可使用固定布局；区域配置包含怪物池、Boss 池、地图效果、奖励和后续地图。

怪物地块在主怪物仍存活时阻止正常揭露相邻地块。钥匙门、迷雾、特殊事件另有交互策略，不宜将全部探索简化成“点一下就翻开六个邻居”。

依据：`CubeMapData.GetAdjacent/CreatMap`、`CellCubeData`、`MonsterCubeInteractive.CanShowAdjacentCell`、地图 SO。

### 3.2 奖励与通行

- 钥匙有三个等级，金币和钥匙使用独立计数。
- 上锁宝箱消耗对应等级钥匙；上锁宝箱进入技能奖励分支。
- 未上锁宝箱按 `getSkillPrecent` 在技能奖励与道具奖励之间选择。
- 技能候选为空时，该宝箱回退为 `(chestLevel + 1) × 20` 金币。
- 门与宝箱的等级字段映射不同：门的 `LevelNeed=2/3/4` 对应钥匙 1/2/3，宝箱为 `1/2/3`，迁移时应统一成明确的 `RequiredKeyId`。
- 区域是否要求击杀 Boss、可到达的下一地图、Boss 后奖励由地图配置决定，不是所有地图都必须清场。

依据：`ChestCubeInteractive`、`LockDoorCubeInteractive`、`ChangeNextSceneInteractive`、`BaseMapDataFile`。

恢复地块按配置数值恢复对应资源，可能受遗物或职业标签修正。驿站则把 HP/MP **补至**指定上限比例，并清除普通技能冷却：默认比例为 100%，难度 3 的基础效果使之变为 65%；已高于该比例时不扣减，也不是再额外恢复 65%。依据：`RecoverCubeInteractive`、`PostStationCubeInteractive`、`TempGlobalParameterData.PostStationRecoverPrecent`。

### 4.2 派生关系

在 `UnitDataManager.CreatUnitDatas` 的属性监听中：

- 力量：每点增加 5 最大生命、0.25 生命恢复；仅在启用 `applyStrengthListen` 的创建路径注册。
- 敏捷：每点增加 0.5 防御。
- 智力：每点增加 5 最大魔力、1 魔力恢复。
- 退出战斗时：技能额外减少 `int(智力 / 3)` 冷却。

恢复结算等多个入口会转为整数，不能只按面板浮点值推断最终结果。代码虽声明“每点敏捷增加 1 初始护甲”的常量，但上述创建方法没有应用它，不应直接写成有效规则。

| 刺客 | 40 / 20 | 4 / 7 / 3 | 0 | 匕首 | 格挡 |

## 5. 战斗时序与行动经济

### 5.1 一场战斗

1. 建立玩家队伍、敌方队伍、场景效果与战斗临时状态。
2. 执行战斗开始事件：场景效果 → 玩家阵营 → 敌方阵营；特定标签可让玩家阵营单位的开始效果执行两次。
3. 全局新轮开始，处理所有单位的基础护甲，轮数增加。
4. 存活的玩家阵营单位先入队，敌方随后入队；不是按速度排序。
5. 选定非玩家单位的技能意图，并计算预览。
6. 逐个执行单位回合：回合开始处理 → 玩家输入或 AI 技能 → 回合结束效果 → 冷却递减。
7. 所有单位结束后，处理默认衰减状态、更新意图、检查死亡和逃离，进入下一轮。
8. 战斗退出时处理结束事件、恢复、额外冷却缩减、临时状态清理，再返回探索或结算。

建议新内核分别命名 `Round`（全体一轮）、`Turn`（单个单位回合）、`Action`（一次指令），防止将三种生命周期合并。

### 5.2 玩家行动

- 默认每回合 **3 行动力**；回合重置为 `最大行动力 + 下回合额外行动力`，随后清除额外量。
- 技能行动消耗来自 `actionCost + 技能实例修正`，玩家入口将负数消耗归零。
- 同时检查技能冷却、战斗/非战斗使用限制、生命或魔力是否足够，以及额外条件。
- 资源消耗类型 `0=魔力，1=生命`；生命不足判定使用 `< cost`，因此等于消耗值时仍允许使用。
- 玩家可主动结束回合。存在 0 行动力技能，不能用“行动力为 0”作为所有情况下的自动结束条件。
- 非玩家单位通常在自己的回合执行一个选定技能；不能把玩家 3 行动力循环直接套给怪物。
- 急速计数至少为 1 时，消耗一次并优先安排该单位的额外回合。

### 5.3 逃跑与死亡

逃跑默认要求至少 2 行动力，同时受禁止逃跑标签限制。进入逃跑状态后结束玩家行动，现有队列继续推进，到下一轮开始前退出战斗；不是点击后立即安全离开。当前入口检查行动力门槛，但没有显式扣除对应点数，应在新规则中明确这一点。

玩家死亡优先判负；敌方无存活单位时判胜。死亡检查先触发自身死亡事件，再检查是否仍死亡，因此存在复活或死亡替代效果的空间。单位死亡还会通知其他单位，可引发连锁效果。召唤物、逃离单位与本体需要分别处理。

依据：`BattleExcuter.StartBattleEvent/AllUnitStartAction/UnitStartAction/UnitEndAction/AllUnitEndAction/BattleOverCheck/ExitBattle`、`BattleOpreate.PlayerUseSkillEvent/SetPlayerEscapingState/JiSuCheck`、`PlayerDataManager.CurActionReset`。

## 6. 护甲、伤害、暴击与闪避

### 6.1 护甲不是百分比减伤

护甲是单独的可消耗整数池 `SheldCount`。普通伤害先消耗护甲，溢出部分扣生命；真实伤害绕过护甲。

普通情况下的每轮刷新分两步：

- 全局轮开始：将不足基础量的护甲补至按防御计算的目标量，暂时不削掉更多的剩余护甲。
- 自身回合开始：把超过目标量的旧护甲压回目标量，再加入“下回合获得护甲”；首次行动还处理初始护甲。
- 有壁垒时保留旧护甲，并在全局轮开始追加本轮基础护甲。
- 战斗退出时清零护甲。

获得护甲的通用修正为 `max(0, int((原始获得量 + 平值修正) × (1 + 百分比修正)))`。不同调用点存在取整与漏用返回值的不一致，见第 12 节。

### 6.2 普通伤害流水线

简化主路径如下，专属效果可以在事件节点上继续修改：

1. 从效果定义求基础伤害：固定值或属性倍率，应用技能等级和技能实例修正。
2. 若为反击，应用反击倍率，默认 0.5。
3. 对普通主动攻击，累计施法者的输出平值/百分比、目标的承伤平值/百分比；目标负防御还增加等值基础伤害。
4. 执行攻击前、伤害设置前等事件，例如寒霜削减伤害。
5. 更新暴击与闪避累计点，并判定本次结果。
6. 非闪避时应用暴击倍率，再消耗护甲与生命；触发受击、受伤、攻击后、反击、死亡等后续事件。

通用输出修正的一段公式为：

`D1 = int(Round((D0 + 输出平值 + 承伤平值 + max(0, -目标防御)) × (1 + 输出百分比 + 承伤百分比), 3))`

这不是完整的所有伤害公式。原作区分主动伤害、被动触发伤害、无来源伤害和道具伤害；各入口不完全相同。多段攻击应逐段结算，不能先乘次数后只做一次护甲、闪避和事件判断。

### 6.3 暴击与闪避是累计机制

- 可暴击的有来源技能伤害：施法者暴击点增加整数精准值；达到 100 时减去 100，标记本次暴击。
- 暴击倍率为 **1.5**，对应伤害转换为整数。
- 受伤入口先给目标闪避点增加整数灵巧值；允许闪避且有来源时，点数达到 100 则本次生命/护甲伤害都为 0。
- **当前代码的特殊行为**：成功闪避时写回 `当前闪避点 - 100 + 灵巧`，即该次命中检查中额外再加一次灵巧。
- 暴击判定在闪避判定之前，意味着一次被闪避的攻击仍可能先消耗暴击点。

“真实伤害”在普通修正与护甲阶段走旁路，但当前代码的真实伤害标志没有直接关闭暴击/闪避；这些还取决于伤害入口和技能类型。因此不能仅据说明文本断言所有真实伤害都不会暴击或闪避。

依据：`UnitData.GetDamage`、`UnitSkillData.GetDamage`、`DamageInfo.GetValue`、`BattleExcuter.DamageTarget/UnitTakeDamage`、`SkillExcute.CanCrit`。

## 7. 技能、武器、遗物与符文

### 7.1 技能定义和实例

定义包含 ID、稀有度、等级上限、主动/被动、类型、生命/魔力消耗、行动消耗、冷却、使用场景、标签、等级参数、主动效果和事件触发效果。

实例另外保存等级、剩余冷却、锁定状态、已装符文、计数器、伤害/次数/消耗/冷却/附加状态层数等修正。定义与实例不是同一份对象。

技能类型配置值：`0=武器攻击，1=魔法，2=被动，4=武技`。原作还有独立被动布尔字段，迁移时需要校验二者一致性。

普通攻击单独保存，不占普通技能数组。英雄配置有 10 个技能槽，初始开放前 5 个，其余基础解锁费用为 **5、10、15、25、40** 金币；难度等还可能增加费用。

### 7.2 等级和冷却

通用参数使用 `参数(L) = 基值 + 每级增量 × L`，不是 `L-1`。消耗、冷却各有同名参数增量，并将结果限制为非负；技能实例修正随后继续作用。

| 配置例子 | 无额外修正时的效果 | 消耗与限制 |
| --- | --- | --- |
| 剑 | `4 + 2L` 固定伤害；1 级为 6 | 行动 1，魔力 0，CD 0 |
| 格挡 | 获得 `4 + L` 护甲；1 级为 5 | 行动 1，魔力 1，CD 0 |
| 奥术飞弹 | `(0.8 + 0.2L) × 智力` 的单段伤害；1 级为 100% 智力 | 行动 0，魔力 4，CD 1 |

正常施放流程是施放前事件 → 执行效果 → 累加冷却/扣资源 → 施放后事件与战斗检查。附加施放可以配置不消耗资源或不进入冷却。

单位回合结束时，普通技能数组中剩余冷却大于 0 的技能减 1。退出战斗还应用智力缩减；普通胜利返回探索的分支另有一次玩家冷却减 1。不能把战后处理简化成“技能全部重置”。

### 7.3 遗物和符文

- 遗物复用技能事件结构，运行时保存在独立集合，同 ID 不重复添加。
- 技能实例只保存一个当前符文字段；符文可修改伤害、次数、行动消耗、冷却等。
- 符文准入可限制主动/被动、是否允许装到等级上限为 1 的技能、匹配技能标签。
- 触发分发中可见的顺序是：状态 → 玩家遗物 → 普通攻击 → 按槽位的技能及其符文。顺序可能影响结果，Core 应显式规定。

主要触发点包括装备/卸装、战斗开始/结束、单位回合开始/结束、施放前后、攻击前后、伤害前后、受击、受伤、击杀、自己死亡、其他单位死亡、使用药水后、反击后、进入新区。伤害、攻击、施放是三个不同层次，不能只保留一个“攻击事件”覆盖全部效果。

依据：`SkillDataConfig`、`SkillDataFile.GetAdditionGlobalParameter`、`UnitSkillData`、`ConstGlobalParameterData`、`RelicBag`、`RuneDataFile.CanSetTargetSkill`、`GlobalEvent.TriggerEvent`。

## 8. 状态系统

状态至少需要：ID、层数、正负面标记、叠加方式、自动衰减开关、战后是否清除、层数参数和事件效果。

原作多数重复施加直接加层；`levelAdditionType=3` 在添加入口取新旧层数的较大值。其他类型值不能仅凭编号猜测“刷新/覆盖/独立持续时间”。自动衰减实际由全局轮结束统一调用，字段名 `turnReduceOnEndAction` 容易误导。

| 状态 | 规则摘要与证据范围 |
| --- | --- |
| 活力 | 提高攻击伤害，层数参与数值；配置及伤害修正机制确认 |
| 易伤 / 虚弱 | 提高承伤 / 降低输出的百分比，自动衰减；百分比由参数决定 |
| 中毒 | 行动开始造成层数相关伤害，再减层；配置标记战后不清除 |
| 烧伤 | 普通路径按层数降低临时生命上限；不是常见的每回合火焰持续伤害 |
| 寒霜 | 普通攻击伤害结算前最多扣除“当前伤害量”的寒霜层数，并按同等数值减伤 |
| 过载 | 行动结束时受到层数相关伤害并移除；配置确认 |
| 荆棘 | 受攻击后对来源造成伤害，自动衰减 |
| 反击 | 受攻击后以普通攻击反击，默认 50% 伤害并消耗层数；避免再次触发无限反击链 |
| 壁垒 | 保留护甲，与基础护甲刷新共同作用 |
| 急速 | 消耗次数获得额外回合 |
| 嘲讽 | 目标选择优先限制在有嘲讽的单位中 |
| 标记 | 配置描述为引导非玩家单位的攻击目标；完整优先级需要结合目标选择入口继续验证 |
| 缴械 | 禁止普通攻击；历史 ID 含 `ChanRao`，不要按拼音误译成其他效果 |
| 束缚 | 禁止逃跑 |
| 眩晕 / 睡眠 | 配置语义为跳过回合；睡眠另有受伤解除，玩家与 AI 行动入口需分别核对 |
| 沉重 | 增加武器/技能行动消耗，使用后减层 |
| 感电 | 受攻击追加伤害并减层，数值来自参数 |
| 灵魂 | 配置的行动开始效果包括魔力恢复、护甲和真实自伤 |

55 条状态文件中混有“力量”“真实伤害”“召唤物”等说明词条，重建时应分开 `StatusDefinition` 与 `KeywordDefinition`。

依据：`BuffConfig`、`BuffListData.AddBuff/ReduceBuffLevel`、`UnitBuffData`、`BuffExcuter`、`GlobalEvent.BuffLevelDefultReduce`、状态 SO。表内未声称逐个专属状态均已运行验证。

## 9. 道具、背包、奖励和商店

### 9.1 背包与道具

英雄 SO 的背包初始数组长度为 8。金币、三种钥匙独立保存；普通物品按 ID 合并数量，找不到同类时占空槽，满包返回失败。具体物品的使用效果由配置事件执行。

道具分类：`-1=基础资源，0=药水，1=技能石`。配置包含基础售价、稀有度、是否仅战斗、是否使用后自动消耗等。通用道具使用入口没有统一扣行动力，但仍受使用阶段、目标与效果条件限制。使用药水还触发“使用药水后”事件，存在重复药效机制。

| 道具 | 参数/效果 | 基础价格 |
| --- | --- | --- |
| 劣质生命药剂 / 劣质魔力药剂 | 恢复 15 HP / 20 MP | 各 10 |
| 生命药剂 / 魔力药剂 | 恢复对应上限的 25% | 各 20 |
| 劣质爆破药剂 / 爆裂药剂 | 对目标造成 25 / 200 伤害 | 7 / 200 |
| 体力药剂 | +1 行动力 | 7 |
| 冷却药剂 | 当前冷却最长技能 CD -20 | 10 |
| 活力药剂 / 易伤药剂 / 毒药剂 | 2 层活力 / 2 层易伤 / 5 层中毒 | 各 15 |
| 冻结药剂 | 为目标附加 20 层寒霜 | 10 |
| 力量 / 敏捷 / 智力强化药剂 | 对应属性永久 +1（局内角色基础值） | 各 35 |
| 初级 / 中级 / 高级技能石 | 提升技能等级，允许的稀有度依次扩大 | 35 / 60 / 90 |
| 突破技能石 | 配置为可忽略技能等级上限；说明排除上限为 1 的技能 | 150 |
| 龙血药剂 | HP 和 MP 各恢复 999，仍受上限约束 | 200 |

这些是配置基础价，不是应用难度与商店修正后的成交价。已核对上述附加状态药剂的目标 ID，均能匹配到对应状态配置。

初级和中级技能石还可以选择同类石头合成：消耗 2 个，得到 1 个下一等级技能石。此选择式道具在确认目标后消费，不能与立即消耗的药水共用简单的“点击即扣数量”实现。

### 9.2 战斗奖励

- 金币按奖励结算列表中的非逃离单位累计基础金币，并加上玩家逐个击杀奖励修正。
- `hardLevel=1` 的单位每个附带一颗初级技能石。
- 药水掉落按怪物等级分组：`组内数量 × [0.10, 0.25, 0]` 得到该组概率；每组最多产生一次掉落，不是每只怪独立掷一次。
- 包含 `hardLevel=2` 时，额外给中级技能石；地图配置允许时，从遗物候选池取一个遗物。
- 实际存在 `hardLevel=3` 的特殊敌人，不能假定所有 Boss 奖励都自动走等级 2 分支。

商店保存本次商品与刷新次数；基础刷新费用为 `5 + 5 × 已刷新次数`。免费刷新、售价修正和商品池另有配置/状态。技能候选与商店选项受玩家当前技能池、职业解锁和稀有度约束。

依据：`BagData`、`ItemManager.UseItem`、`GlobalEvent.PlayerUseItem/GetBattleEndReword`、`ConstGlobalParameterData.GetRefrashShopCost`、`TempDataManager.CurShopDatas`、道具 SO。

## 10. 怪物、AI 与召唤

怪物定义共用单位属性、普通攻击、技能、体型、标签，同时有 `battleAIKey`、击杀金币/灵魂字段、等级和终局标志。字段存在不代表所有奖励路径都使用它，例如主战斗奖励路径未按 `canGetSoul` 直接发放灵魂。

| 例子 | 配置等级 | 基础HP | 基础MP | 击杀金币 | AI |
| --- | --- | --- | --- | --- | --- |
| 野狼 | 0 | 25 | 100 | 5 | 默认 |
| 巨熊 | 1 | 55 | 100 | 15 | 默认 |
| 森林巨猿 | 2 | 150 | 100 | 30 | 默认 |
| 丛林守护者 | 2 | 400 | 120 | 30 | 专属 |
| 多头蛇 | 2 | 750 | 50 | 30 | 专属召唤选择 |
| 哥布林之王 | 3 | 2000 | 350 | 100 | 专属 |

以上是 SO 原始值，地图难度、被动、召唤构造会改变实际属性。

默认 AI 从可用主动技能和允许的普通攻击中随机选择。非重新随机检查时尽量保留已有意图；并非每次刷新 UI 都重新掷一个技能。默认候选检查会忽略资源消耗，不能直接等同于玩家可用性检查。

怪物创建时还会从技能管理器取得初始冷却，而非保证所有主动技能开局就绪。普通攻击的难度调整作用于技能等级：按 `int(原等级 × 倍率)` 计算；倍率大于 1 而截断后等级没变时额外加 1。

专属 AI 通过注册的 key 选择策略。例如多头蛇根据己方队伍数量选择召唤：队伍不少于 3 时概率 0；为 2 时 25%；更少时 100%。队伍计数包含自身。另有指定回合后优先技能等策略，但其中发现疑似实现问题。

召唤物有独立单位实例、阵营、体型与行动；幻象另有复制属性的逻辑。当前召唤容量检查连接 UI/单位表现对象，新内核应自己判定阵容容量，再通知 Unity 创建视图。

依据：`UnitBaseDataConfig`、`UnitDataFile`、`BattleExcuter.GetUnitCanUseSkillData`、`BaseAIBehavior`、`DuoTouShe_3006_AIBehavior`、`UnitDataManager.CanCreatUnit`。

## 11. 难度、局外成长与存档

难度按级累计前面各级效果：

| 新增等级 | 代码效果 |
| --- | --- |
| 1 | 普通怪生命系数 +0.40、精英 +0.25、Boss +0.20 |
| 2 | 商店价格系数 +0.25 |
| 3 | 驿站恢复比例 -0.35 |
| 4 | 怪物普攻等级倍率从 1 增至 1.3（有取整补偿），其他技能等级修正 +1；不等于所有伤害直接 +30% |
| 5 | 技能槽解锁附加费用 +15 |

局外经验的结算主路径：

- 到达区域项：使用当前地图等级减 1，值大于 0 时为 `100 + 50×该值`，否则为 0；不是逐区域累计求和。
- 击杀项：等级 0/1/2 分别按 10/20/50 经验累计。
- 难度倍率：`1 + 0.2×难度`。
- 通关倍率 1.5，失败倍率 1。
- `GetMainExp` 将非倍率项目相加，再乘倍率项目。其他扩展奖励入口可能继续增加项目。
- 英雄成长点升级需求为 `300 + 200×目标等级`；从 0 点取得第 1 点需要 500 经验。

局内状态与局外进度分开：局内保存角色、技能及符文/计数器、背包、遗物、地块状态、怪物组、商店与事件参数等；局外保存英雄经验/天赋点、解锁、难度、成就和图鉴。原作在进入普通怪战斗前保存，不应未经验证就承诺支持战斗中任意时刻完整恢复。

依据：`HardLevel01..05`、`GamePrograssAndHardManager.ExcuteHardEffect`、`ExperienceCalculation`、`HeroExpInfo`、`GlobalEvent.GameOver/SaveCurGameData`、各 SaveConfig。

## 12. 需要保留记录、但不宜直接复制的行为

| 发现 | 已看到的证据 | 重建处理建议 |
| --- | --- | --- |
| 闪避成功额外加一次灵巧 | `UnitTakeDamage` 先加点，成功后又 `-100+灵巧` | 明确是否忠实保留，提供边界用例 |
| 暴击点在闪避前消耗 | 同一方法中的执行顺序 | 在伤害规则中显式定义 |
| 真实伤害的文案过于绝对 | 实现只旁路部分修正与护甲，未统一关掉暴击/闪避 | 独立定义可暴击、可闪避、忽略护甲等标志 |
| 反击分支重复安排施放后回调 | `UseSkill` 的 CounterAttackTag 分支内外均入栈 | 核查是否造成双触发，不作为默认新规则 |
| 特定 AI 候选循环不会执行 | `MustUseSkillAfterTurnAIBehavior` 遍历刚创建的空列表的 Count | 视作疑似缺陷，按明确策略重写 |
| 初始护甲计算未采用修正返回值 | `UnitStartAction` 调用 `GetResultArmor` 后仍使用原变量 | 统一护甲数值入口 |
| 防御取整不统一 | 全局轮开始使用 Round，自身回合开始使用 int | 统一数值精度和取整政策 |
| 战后恢复读取玩家属性给存活单位 | `ExitBattle` 遍历单位但读取 playerData 的恢复值 | 区分“全队共享”与“单位自身恢复” |
| 自动 Buff 衰减字段名与时机不一致 | 调用在全局轮结束，`isEndTurn` 参数未参与分支 | 以显式 TickPhase 表达 |
| 同类状态重复 / 说明词条混用 | 亢奋有两套 key；属性词条也使用 Buff 结构 | 内容校验、别名迁移，分离词条 |
| 难度经验有两种定义 | HardData 每级 0.1，结算主路径使用每级 0.2 | 以明确的结算公式为基准，查调用再删旧定义 |

这些来自静态分析，不等于已经通过实机重现的全部 Bug。暂不声称完成每个技能、遗物、剧情节点及交互组合的运行验证。

## 13. 对 Dungeon 的数据驱动边界建议

这是新项目建议，与上面的原作事实分开。

数据链路应为：**Unity 的 SO 资产 → 适配层校验和转换 → 纯 C# 定义集合 → Core 创建运行时状态 → 输入指令并输出结果事件 → Unity 展示。**

| 内容 | SO / Unity 适配层 | 纯 C# Core |
| --- | --- | --- |
| 人物、怪物 | 编辑初始属性、技能 ID、掉落、AI 参数 | UnitDefinition 与 UnitState，阵营、存亡、属性派生 |
| 技能、状态、遗物、符文 | 编辑参数、条件、触发点、效果序列 | 校验使用条件，执行效果，处理层数与生命周期 |
| 道具与经济 | 配置售价、使用效果、候选池 | 背包、购买、消耗、抽取与奖励结算 |
| 地图 | 配置地块、拓扑、生成规则和事件 | 揭露、可达性、交互条件、进度与随机结果 |
| 美术与交互 | Sprite、Prefab、动画、音效、输入、UI | 仅稳定 ID、数值和结果，不引用美术类型 |
| 随机与存档 | 提供种子、文件读写和版本迁移入口 | 可注入随机源、可序列化状态与恢复规则 |

Core 中不应出现 `ScriptableObject`、`UnityEngine.Object`、`MonoBehaviour`、`Sprite`、`Vector2Int`、`UnityEngine.Random`、协程或 UI 引用。用自己的坐标值类型和普通 C# 数据类型。SO 转换成独立定义数据；运行时 HP、CD、Buff、背包不得写回共享 SO。

仅把数值放进 SO 还不够：若每个技能效果仍写死在 Unity 脚本里，规则依旧没有进入 Core。建议 SO 使用明确的效果类型、目标选择、条件和参数；Core 用受控的效果执行器处理。复杂 Boss 使用 Core 中注册的 AI 策略，SO 选择策略及参数即可，不必一次构建任意脚本解释器。

建议的最小验证闭环：单英雄 → 野狼 → 剑/格挡/奥术飞弹 → 中毒/壁垒/反击 → 战后奖励 → 返回探索。首先验证回合顺序、取整、事件连锁和配置不可变性，再扩大技能池。

当前六边形棋盘若继续使用，应作为 Dungeon 的新规则选择：邻接、揭露、路径、障碍和生成都通过拓扑定义进入 Core。战斗本身可继续参考原作的独立双方队伍模式；原作没有提供六边形战场移动规则可直接照搬。
